## Evidencia
- CLI (`count --filter`, `delete-by-filter`): exige `{"field": {"$eq": value}}` — rechaza plano: `Filter value ... must be an object like {"$eq": value}`
- MCP `search_memory` filters: exige `{"field": value}` plano — rechaza `$eq`: `metadata field ... has unsupported type object`
- Formatos **invertidos** entre interfaces

## Contrato
"decisión de formato canónico documentada; AMBOS canales aceptan el formato canónico sin romper la API existente (evaluar aceptar los dos formatos: detectar `$eq` vs plano y normalizar); tests para ambos canales"

## Herramientas necesarias
- cargo-mcp (nextest, check), codegraph_explore (parseo de filtros en CLI y MCP)

## Investigation Notes
Dos opciones:
1. **Canónico = operadores (`{"field": {"$eq": value}}`)** — más expresivo (permite $gt/$lt/$in futuro), pero es el formato CLI actual.
2. **Canónico = plano (`{"field": value}`)** — más simple, formato MCP actual.

Recomendación: **aceptar AMBOS** en ambos canales (normalizar en un punto común): si el valor es un objeto con una sola key `$op`, interpretar como operador; si es un valor plano, interpretar como igualdad. Así ningún cliente existente se rompe y la API queda consistente. Documentar el formato canónico en la skill y en `docs/api/`.

**NO cambiar** la semántica de los operadores existentes ni romper clientes.

## Decisión (documentada 2026-08-18)

**Formato canónico: AMBOS formatos son aceptados en ambos canales, normalizados en el punto de parseo.**

| Formato | Significado | CLI (`parse_filter_json`) | MCP (`parse_filter_ops` nueva) |
|---|---|---|---|
| `{"field": value}` plano | igualdad (`$eq` implícito) | ✅ aceptado (NUEVO — antes rechazaba) | ✅ aceptado (ya lo hacía via parse_metadata) |
| `{"field": {"$eq": v}}` operador | igualdad explícita | ✅ aceptado (ya lo hacía) | ✅ aceptado (NUEVO — antes rechazaba) |
| `{"field": {"$gt": v}}` etc. | operadores de rango | ✅ aceptado (ya lo hacía) | ✅ memory_list acepta via `filter_ops` (core ya soporta); **search_memory** devuelve error claro (el request de search no tiene slot filter_ops — `VantaMemorySearchRequest` flat-only, 37 sitios, hot path; no se toca el motor) |

**Backward compat garantizada:**
- CLI: el formato operador (publicado) sigue funcionando; plano ahora es alias de `$eq`.
- MCP: el formato plano (publicado) sigue funcionando idéntico; `$eq`/operadores en memory_list se mapean a `filter_ops` con la MISMA semántica de igualdad.
- `parse_metadata` (tools.rs:272, memory_put metadata) NO cambia — los metadatos de escritura siguen plano-only.
- Test MCP existente que rechaza `{"nested": {"a": 1}}` (mcp_tests.rs:1589) sigue pasando: `a` no es operador conocido → "Unknown filter operator 'a'".

**Racional:** el core SDK ya tiene ambas primitivas — `matches_memory_filters` (plano, serialization/mod.rs:476) y `matches_advanced_filters` (operadores, serialization/mod.rs:485). `VantaMemoryListOptions` ya tiene `filter_ops`; `VantaMemorySearchRequest` NO (flat-only). No se toca el motor de search (Regla 0, hot path) — se normaliza en los parseos.

**Límite conocido (vanta-review minor #1, aceptado):** la igualdad CLI es escalar-only (`json_to_vanta_value` acepta String/Number/Bool; `null`/listas fallan en CLI flat y en operadores CLI) mientras MCP flat acepta null/listas. Asimetría pre-existente — el flat CLI reusa la conversión del operador CLI existente, consistente intra-canal. No se amplía el set de tipos de `json_to_vanta_value` en este PR (Regla 0: cambio de contrato de tipos, fuera del scope de AUD-048). Si un bug report lo reclama, es un PR aparte que unifica `json_to_vanta_value` ↔ `json_value_to_vanta_value`.
