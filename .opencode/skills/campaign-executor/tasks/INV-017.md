## Investigation Notes
- **Hecho verificado:** `rg -rln sccache .github/` → 0 resultados. sccache NO está implementado. `.opencode/AGENTS.md` (sección "CI: sccache") afirma "Agregado al workflow ci-rust-10.yml mediante mozilla-actions/sccache-action" — DRIFT documental a corregir.
- **Compatibilidad:** SÍ. `mozilla-actions/sccache-action@v0.0.11` + env `SCCACHE_GHA_ENABLED=true` + `RUSTC_WRAPPER=sccache`. Backend = GHA cache (sin infra adicional; ACTIONS_CACHE_URL/ACTIONS_RUNTIME_TOKEN se inyectan solos).
- **Complementarios vs redundantes:** Swatinem/rust-cache cachea `target/` entero (blob grande, restore lento, invalida todo al cambiar Cargo.lock). sccache cachea objetos compilados individuales (granular; comparte `.rlib` entre jobs paralelos del mismo run — clippy/test/coverage compilan los mismos crates). Ambos compiten por el límite de GHA cache (10GB, eviction LRU 7 días).
- **Estado CI actual (baseline run 30731463004):** bottleneck = Tests (Windows) 14m29s, causado por `cargo install cargo-nextest --locked` (ci-rust-10.yml:138) en vez de `taiki-e/install-action` como Linux/macOS. El resto del CI ya usa cargo check + nextest + jobs paralelos.
- **Veredicto ROI:** sccache = barato de integrar pero ahorro de wall-clock modesto (0-15%) sobre el CI ya cacheado. El fix del nextest de Windows es el mayor ROI (~4-5 min del bottleneck = ~30% del run). Ambos juntos cumplen el DoD del 20% de GH-143.
