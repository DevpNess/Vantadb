# Task ERR-037 — batch_insert single exists-check

- **Estado:** ✅ COMPLETED
- **Commit:** `b97c0ccd perf(ERR-037): batch_insert single exists-check` + follow-up `perf(ERR-037): probe bookkeeping-only meta with chunked locks`
- **Fecha:** 2026-08-10 (core) / 2026-08-11 (FASE PERFORMANCE + follow-up fix)

## Descripción

`batch_insert_with_opts` llamaba `self.get(n.id)` por cada nodo en el rayon path (10k batch = 10k read-paths completos): active-txn lock, cache **write** lock, KV metadata read, HNSW lookup, vstore mmap vector read + clone descartado. Optimizar el existing-check.

## Solución (core, b97c0ccd)

Nuevo probe `existing_for_batch(id)` en `src/storage/engine/ops.rs` que devuelve solo `relational` + `edges` (todo lo que necesita el bookkeeping de cardinality/edge/scalar index):

1. **Read-your-writes**: chequea active txn buffer primero (paridad con `get()`).
2. **Cache**: `volatile_cache.read()` compartido — sin write lock, sin bookkeeping de hits (probe, no read).
3. **Backend**: solo lee el blob de metadata KV (`deserialize_node_payload`), nunca el vector en vstore.

Se reemplazó `self.get(n.id).unwrap_or(None)` por `self.existing_for_batch(n.id)` en el rayon path (`par_iter`, mantiene paralelismo) y en el non-rayon path (`if let Some(existing_node)`).

`skip_existing_check` ya existía en `BatchInsertOptions` y es usado por bulk loaders (`src/sdk/api.rs:277`, benches) — se mantiene como opción para inserts puros; el default conserva el check porque `batch_insert` público es upsert-safe.

### Hallazgos del proceso (investigación de una "regresión" que resultó artefacto de benchmark)

1. **Primera medición parecía regresión overwrite (+146%)** → la causa era doble:
   a. El bench original creaba nodos con tier **Cold** (default de `UnifiedNode::new`), así que la pre-inserción **nunca poblaba el cache** → el escenario overwrite medía el path de backend-miss, no el cache-hit que ERR-037 optimizaba. Corregido: `make_nodes` setea `tier = NodeTier::Hot`.
   b. El probe original de b97c0ccd clonaba el `UnifiedNode` completo (vector 768-d incluido) en cache-hit → contención de allocator bajo read-lock compartido. Fix: `ExistingMeta { relational, edges }` — clona solo lo que el bookkeeping consume.
2. **Lock-per-node seguía caro** → `par_chunks(256)` amortiza `active_txns` + cache locks a ~40 adquisiciones por batch de 10k (sin cambio semántico: mismo orden txn-buffer → cache → backend).
3. **Instrumentación temporal** (eprintln por fase) probó: probe = 1-3ms, el loop de decremento de cardinality_stats = ~35-40ms (costo **pre-existente** de la semántica correcta, no del probe; candidato a optimización futura, fuera de scope ERR-037).
4. **Verificación de paridad**: el `get()` pre-fix devolvía `None` en el bench Cold (HNSW vacío en Rebuild mode) → el decremento nunca corría → el "before" de 31.8ms era artificialmente rápido. Con medición justa (Hot), el pre-fix real es 97.14ms y el fix lo baja a 67.68ms.

### Resultado
- Probe (cache-hit): 1-3ms para 10k nodos (antes ~30ms+ de get() con write-lock serializado).
- Overwrite/upsert path: **−30.3%**. Fresh path: flat (dentro del ruido).
- Deuda documentada: loop de decremento de `cardinality_stats` (~35ms en overwrite 10k) — pre-existente, separar como optimización futura (batch de stats en vez de retain por nodo).

## Context Save

- **Decisión clave**: probe barato > batch-get masivo. `existing_for_batch*` devuelve solo metadata (relational/edges), nunca vector, preservando paridad de orden con `get()` (txn buffer → cache → backend). Tombstone-en-disk pero KV-presente converge como before (index removes no-op).
- **Decisión de benchmark**: los escenarios de overwrite deben usar tier Hot para ejercitar el cache-hit path real — tier Cold (default) deja el cache vacío y mide backend-miss, artefacto que hizo parecer el "before" más rápido de lo real.
- **Deuda futura**: decrement loop de cardinality_stats (~35ms/10k overwrite) — batching de stats propuesto; fuera de scope ERR-037.
