# DRV-004: `list()` carga ALL records a memoria antes de paginar

**Archivo:** `src/sdk/api.rs:266-276` + `src/sdk/serialization/impl_export.rs:65-107`

**Problema:** `list()` llama `self.records_for_namespace(namespace, &options.filters)?` que carga TODOS los records del namespace en un `Vec<VantaMemoryRecord>` (impl_export.rs:79). La paginación ocurre DESPUÉS en api.rs:268-271 como simple slicing. Namespace con 100K+ registros → OOM.

## Acceptance Criteria

1. `list()` no carga todos los records a memoria — usa paginación server-side (cursor por batch)
2. `records_for_namespace()` se mantiene para export_namespace / export_all (necesitan full data) 
3. Nuevo método `list_records_paginated()` (o similar) que itera por batches desde el engine
4. La paginación debe ser cursor-based, no offset-based (evita O(n) scan offset)
5. Compatibilidad backward: `VantaMemoryListPage` y `next_cursor` APIs no cambian
6. Unit tests para: página única, paginación secuencial, cursor final (None), namespace vacío

## Callers afectados

- **records_for_namespace()** (impl_export.rs:65) — 6 callers en: impl_export.rs (export_namespace, export_all), search/mod.rs (search_keys, search_keys_with_namespace, search_keys_with_filters), api.rs (list)
- **list()** (api.rs:258) — multiple callers en Python SDK, TS SDK, WASM, MCP, CLI

**Solución propuesta (ponytail):**
1. `records_for_namespace()` se queda como está para exports
2. `list()` usa nueva fn `list_paginated()` que itera `indexed_ids_by_namespace()` / `indexed_ids_by_filter()` en chunks de `limit` (default 100) y solo materializa los nodos del chunk actual via `engine.get_many()`
3. El cursor interno usa índices sobre el vector de IDs (vector ya en memoria es pequeño — solo u128s, ~1.6MB por 100K)
