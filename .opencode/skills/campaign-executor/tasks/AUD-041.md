## Investigation Notes

- **Path ListFloat (ADR-019 / P2-7):** write = `sparse_vector_to_field` (`src/sdk/serialization/mod.rs:252`) interleaves `[dim, weight, dim, weight, ...]` como `Vec<f64>` → `FieldValue::ListFloat`; read = `sparse_vector_from_field` (:264) valida y reconstruye BTreeMap. Ambos son **privados** — el bench (crate externo) no puede llamarlos directamente.
- **Decisión de diseño:** los arms serde_json existentes inlinean `serde_json::to_string`/`from_str` (primitivo puro, sin wrapper de record). Para comparación apples-to-apples en critcmp, los arms ListFloat miden el mismo nivel de abstracción: inline del loop de interleave/deinterleave, con comentario que referencia los helpers privados ADR-019 (mismo patrón que ya usa el arm viejo con serde). No se usa `memory_record_from_node` (público) porque mediría overhead de record completo (fields, TTL) no el primitivo ListFloat.
- **Dataset:** la tarea pide dataset representativo para ListFloat (lista densa de f32). Se usa un `SparseVector` denso con TODOS los dims del vocabulario (`VOCAB=2000`), distinto del sample sparse (24 NNZ) del arm viejo.
- **API verificada:** `SparseVector(pub BTreeMap<u32, f32>)` — campo `.0` público, accesible desde bench. `SparseVector::new()` + `.insert()` ya usados por el bench.
