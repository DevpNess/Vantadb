## DISCOVERY — Verificación del estado real

### 1. Fallback silencioso confirmado (lib.rs:208-219)

`new()` mapea `Some(other)` → `tracing::warn!` + `BackendKind::Fjall`. Un typo como `backend="rocksdb "` o `backend="roksdb"` abre la DB con Fjall sin error: la app persiste en un backend distinto al pedido, silenciosamente.

```rust
Some(other) => {
    tracing::warn!("Unknown backend {:?}, falling back to default backend fjall", other);
    vantadb::BackendKind::Fjall
}
```

La docstring de clase (L59-61) documenta el fallback: "Unknown values fall back to the default backend with a warning" — el contrato actual *declara* el warning. La corrección cambia contrato → docstrings se actualizan (L59-61 y L177-179). `#![warn(missing_docs)]`: los helpers nuevos llevan `///` docs.

### 2. Duplicación new()/connect() confirmada

- `new()` L200-233: `#[pyo3(signature = (db_path, memory_limit_bytes=None, read_only=false, backend=None))]`; struct literal `VantaConfig { storage_path, memory_limit, read_only, backend_kind, ..Default::default() }` (L220-226); `py.detach` + `VantaEmbedded::open_with_config(config).map_err(map_vanta_error)?`; wrap `VantaDB { engine, op_gate: OpGate::new() }`.
- `connect()` L1916-1935: `#[pyo3(signature = (path, memory_limit=None))]`; re-imports locales `VantaConfig`/`VantaEmbedded` (L1919-1920); normalización `""`/`":memory:"` → `":memory:"` (L1922-1926); mismo struct literal (sin read_only/backend_kind), mismo open, mismo wrap.

Única diferencia semántica: `connect` normaliza; `new` pasa `db_path` crudo. El SDK no special-casea `:memory:` en `storage_path` → la normalización vive en el binding y queda en `connect`.

### 3. Impacto

- `connect()` no expone `read_only`/`backend` → helper compartido con defaults `false`/`None` preserva la API Python.
- `PyValueError` ya importado (usado en `parse_search_method`) → sin imports nuevos.
- Tests Python: único match de `backend=` es `test_sdk.py:296` (`search_with_method`, ajeno al fallback).
- `parse_search_method` NO se toca.

## Decisión

- `parse_backend_kind(backend: Option<&str>) -> PyResult<vantadb::BackendKind>`: `None`→Fjall, `"rocksdb"`→RocksDb, `"memory"`→InMemory, otro→`PyValueError` descriptivo.
- `open_vantadb(py, storage_path: String, memory_limit: Option<u64>, read_only: bool, backend: Option<&str>) -> PyResult<VantaDB>`: construye config + abre con `py.detach` + wrap. Preserva la semántica por call-site: `new()` pasa `db_path` crudo; `connect()` normaliza antes de llamar.
- Docstrings: "Unknown values fall back..." → "Unknown values raise ``ValueError``."

## Hallazgo colateral (fuera de scope, pre-existente)

`VantaDB(':memory:')` con backend default (`None` → fjall + `storage_path=":memory:"`) lanza `OSError (os error 123)` en Windows: Fjall trata `":memory:"` como directorio literal. Comportamiento idéntico antes del refactor (verificado con el módulo stale: mismo error en el path de fallback). El docstring solo ejemplifica `VantaDB(":memory:", backend="memory")`, y ningún test cubre el caso default — no es regresión de AUD-037. Decisión: no tocar (alteraría semántica del binding fuera de scope); queda registrado para que el orquestador decida si abre un finding.
