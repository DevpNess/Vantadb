# ERR-015 — 🔵 `kill()` siempre en `request_shutdown` (sin señal graciosa)

**Estado:** ✅ COMPLETED (reabierto 2026-08-12 — Windows gap cerrado)
**Commit previo:** `704f2a67` — fix parcial (Unix SIGINT).
**Commit final:** `63e0f9ec` — `fix(ERR-015): graceful shutdown via stdin EOF before kill in request_shutdown`

## Problema
`request_shutdown` en `desktop/src-tauri/src/connections/child_process.rs:170-189`:
- **Windows**: `#[cfg(windows)] let _ = &grace;` → `kill()` directo (TerminateProcess) sin
  señal graciosa → el sidecar MCP no alcanza a flushear su storage engine → riesgo de
  metadata loss (WAL/pending writes).
- **Unix**: SIGINT existente, pero SIGINT solo no saca un child **idle** — el loop de
  `run_stdio_server` está bloqueado en `lines.next_line().await`
  (vantadb-mcp/src/lib.rs:522-531) y solo rompe en stdin EOF (`Ok(None) => break`, L526);
  el flag `running` del handler `ctrl_c` solo se chequea *después* de procesar un request (L591).

## Fix (mínimo, ponytail)
Cerrar **stdin primero** — el hijo MCP consume stdin y rompe su loop en EOF; tras
`run_stdio_server` retornar, `vantadb-server` main.rs:58-65 **flushea storage** antes de
salir. Es el único mecanismo gracioso per-process disponible en Windows (no hay API de
señal), por eso es el path primario en TODAS las plataformas:

1. `drop(self.child.stdin.take())` — EOF → child rompe loop → flush → exit clean.
2. `#[cfg(unix)]` SIGINT como belt-and-suspenders (mismo path de flush vía ctrl_c).
3. `tokio::time::timeout(grace, self.child.wait())` — ventana de gracia.
4. Backstop: force-kill + reap si el child ignora EOF/SIGINT o cuelga.

Sin deps nuevas, sin APIs inventadas (`Child.stdin` es `Option<ChildStdin>` público —
ya se usa `child.stderr.take()` en L119). No toca `src/` raíz (workspace desktop aislado).
