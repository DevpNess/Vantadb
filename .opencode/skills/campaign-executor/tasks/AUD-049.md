## Evidencia
- PyPI paquete: `vantadb-py` 0.5.0; módulo instalado: `vantadb_py` (verificado: `import vantadb` → ModuleNotFoundError; `import vantadb_py` → OK)
- Rust crate y npm package se llaman `vantadb` — el módulo Python no coincide
- README usa `import vantadb_py as vdb` — correcto pero frustrante para quien asume `import vantadb`

## Contrato
"decisión documentada: alias `import vantadb` (re-export en `__init__.py` o package name) O documentación explícita; `import vantadb_py as vdb` existente NO se rompe; quickstart sin fricción"

## Herramientas necesarias
- terminal (python, pip), grep (referencias a `vantadb_py` en integraciones), webfetch (docs PyO3 module name si hay duda)

## Investigation Notes
Opciones:
1. **Alias en `__init__.py`**: `vantadb_py/__init__.py` podría exponer `vantadb` como alias — pero en Python el `import vantadb` busca un módulo/paquete llamado `vantadb`, no un símbolo dentro de otro módulo. El alias real requiere un shim `vantadb/__init__.py` que re-exporte `vantadb_py`, o renombrar el module-name del pyo3.
2. **Renombrar module-name a `vantadb`**: pyproject `module-name = "vantadb"` — rompe TODAS las referencias a `vantadb_py` (integraciones, docs, tests). Alto impacto.
3. **Documentar + shim**: crear un paquete `vantadb` (shim delgado) en el wheel que haga `from vantadb_py import *` — permite `import vantadb` sin romper `vantadb_py`. Es lo más seguro.

**Verificar ANTES**: `grep -r "vantadb_py" vantadb-python/ integrations/ packages/` para mapear todas las referencias. No tocar sin mapear (Regla 0).
