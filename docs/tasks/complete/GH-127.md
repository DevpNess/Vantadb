## Descripción

El WAL es crítico para durabilidad. No existe coverage property-based del
roundtrip de `WalRecord`: solo hay un test manual de variantes
(`tests/core/snapshot_certification.rs::wal_record_all_variants_roundtrip`) y
un no-panic test sobre bytes aleatorios (`tests/fuzz_proptest.rs`). Falta
probar que **cualquier record válido generado al azar** sobrevive
serialize→deserialize con el mismo valor, en todos los tamaños de payload y
bajo escrituras concurrentes.

## Contrato (verificable por comando)

```bash
cargo nextest run --profile audit -p vantadb --test proptest_wal_roundtrip --build-jobs 2
```

Exit 0 y al menos 1000 casos proptest ejecutados en la propiedad de roundtrip
(puro, en memoria). Archivo de test nuevo: `tests/proptest_wal_roundtrip.rs`.

## Datos de contexto (ya investigados)

- `WalRecord` (`src/wal.rs:33`): enum de 7 variantes — `Insert(UnifiedNode)`,
  `Update{id,node}`, `Delete{id}`, `Checkpoint{node_count,index_checksum,timestamp}`,
  `Begin(u64)`, `Commit(u64)`, `Abort(u64)`. Derives: `Serialize, Deserialize,
  Debug, Clone` — **sin `PartialEq`**.
- `UnifiedNode` (`src/node.rs:992`) **sí** tiene `PartialEq` → se puede derivar
  `PartialEq` en `WalRecord` sin cascada (u64/u128/u32/Option<u32> ya lo tienen).
  Alternativa sin tocar producción: roundtrip por igualdad de bytes postcard
  (`to_allocvec(deserialized) == bytes_originales`). Preferir bytes-equality;
  `PartialEq` solo si facilita las assertions.
- `WalWriter` (`src/wal.rs:177`): `open(path, SyncMode)`, `append(&WalRecord)`,
  `batch_append(&[WalRecord])`, `sync()`. **No es Sync** (`&mut self`).
- `WalReader` (`src/wal.rs:555`): `open(path)`, `next_record() -> Result<Option<WalRecord>>`,
  `replay_all(handler)`.
- `UnifiedNode::new(u128)`, `with_vector(u128, Vec<f32>)`, `set_field(k,v)`;
  campos pub `ext_metadata: HashMap<String,Vec<u8>>`, `relational: BTreeMap<String,FieldValue>`.
- Guard de lectura: `WalReader` rechaza `len > 10_000_000` (`src/wal.rs:605`).
  Cap "near-max" en ~1 MB para no relentizar el proptest.
- `proptest = "1.5"` ya es dev-dep (`Cargo.toml:172`). `tempfile` ya se usa en tests.
- Test runner: `cargo nextest run --profile audit --workspace --build-jobs 2`
  (Windows: SIEMPRE `--build-jobs 2`).
- Los tests de raíz (`tests/*.rs`) corren en la suite normal; `fuzz_proptest`
  está excluido de nextest y corre solo en heavy-certification.

## Pasos atómicos

1. **Proptest 1 — roundtrip bytes puro** (`ProptestConfig::with_cases(1000)`):
   estrategia que genera un `WalRecord` válido arbitrario (todas las variantes),
   `to_allocvec` → `from_bytes` → re-serialize → bytes idénticos. Cero I/O.
2. **Proptest 2 — tamaño de payload**: generar records cuyo payload serializado
   caiga en buckets: ~0 B (Begin/Commit/Abort), 1 B, 64 KB y near-max (~1 MB,
   vía `Insert` con `ext_metadata`/`relational`/vector grande). Mismo roundtrip
   bytes. `with_cases` moderado (≤100).
3. **Proptest 3 — file roundtrip**: generar un batch aleatorio de records,
   `WalWriter::batch_append`, reabrir con `WalReader`, verificar que cada record
   leído existe en el batch original (comparación por bytes). `with_cases` ≤50.
4. **Test 4 — escrituras concurrentes** (no proptest si es frágil): generar
   N×M records, escribir desde threads con `Arc<Mutex<WalWriter>>`, reabrir y
   verificar multiset completo de bytes. Counts deterministas.
5. Verify: clippy `--all-targets -D warnings`, `cargo fmt --check`, nextest del
   archivo nuevo. NO editar código de producción si no hace falta.
