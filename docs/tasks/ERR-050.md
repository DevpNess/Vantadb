# ERR-050 — WAL multi-shard: next_shard no persiste entre opens → CLI real falla al 3er comando write

## Estado: PENDING → delegado a vanta-worker

## Síntoma
`tests/cli_tests.rs` (COV-003, commit f71dbff9): 3 tests fallan con el mismo error al REABRIR read-write:
```
WAL shard 1 is truncated: 0 durable records, but round-robin requires at least 1; aborting recovery instead of silently dropping data
```
Tests: `test_delete_record`, `test_delete_verbose`, `test_count_with_filter`.
Los tests que solo reabren read-only (get/list) PASAN — `recover_state` (init.rs:419) salta la WAL en read-only.

## Causa raíz (trazada)
1. `cmd_put` (crud.rs:26) → `open_database` → `StorageEngine::open_with_config` → `init_wal` → `ShardedWal::new`
2. `ShardedWal::new` (wal_sharded.rs:173) inicializa `next_shard = AtomicUsize::new(0)` **en memoria**
3. Cada comando CLI = proceso/open nuevo → `next_shard` vuelve a 0 → el 2º put cae en **shard 0** otra vez
4. Con `wal_shards=4` (default, config.rs:758): shard_counts = `[2,0,0,0]`
5. 3er open read-write: `recover()` → `verify_shard_counts` (ERR-011, commit 86490dd2): `max_count=2`, shard 1: `0+1 < 2` → **aborta recovery**

## Impacto real
`vanta-cli put` → `vanta-cli put` → `vanta-cli delete` en la misma DB (uso normal del CLI, 3 procesos) FALLA con WAL multi-shard. ERR-011 (86490dd2) convirtió el bug latente pre-existente en error duro.

## Por qué nadie lo vio
- `cli_tests` está EXCLUIDO del default-filter de nextest (.config/nextest.toml)
- El contrato del plan COV-003 (`--profile audit`) hereda ese filter → nunca corrió los tests CLI

## Fix propuesto (mínimo, a validar por vanta-worker)
Al abrir un WAL existente, derivar la posición round-robin de los records durables:
`next_shard = (total_records_durables % num_shards)` tras la recovery, en vez de 0.
O persistir next_shard en shard_meta (write_shard_meta) al cerrar/checkpoint.

## Verificación
```powershell
$env:RUST_MIN_STACK="16777216"
cargo test -p vantadb --features cli --test cli_tests --jobs 2
```
Deben pasar los 50+ tests (actualmente 3 fallan).
Luego re-verificar WAL unit tests: `cargo test -p vantadb wal_sharded`

## Contrato de aceptación
- `cargo test -p vantadb --features cli --test cli_tests --jobs 2` → todos pass
- `cargo test -p vantadb wal_sharded` → todos pass
- No romper recovery de DBs existentes con shard_counts válidos
