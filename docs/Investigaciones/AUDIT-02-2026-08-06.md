## 2. Medición

**Bench:** `benches/sparse_hot_path.rs` (criterion, profile `bench`, sample_size=20).

**Dataset:** 5.000 docs con sparse vectors de ~24 dims no nulas sobre un vocabulario de
2000 dims (~1.2% densidad). Query con dims calientes y/o compartidas que materializan
**5.000 candidatos** (todas las docs del namespace). top_k=10 (chico, como el contrato).

| Benchmark | Tiempo mediana | Nota |
|---|---|---|
| `sparse/hot-path/search_total_top10` | **464.22 ms** | Hot-path completo end-to-end (posting scan + decode + get_many + `memory_record_from_node` + sort) |
| `sparse/hot-path/sort_full_candidates` | **2.3748 ms** | Sort completo de los 5.000 candidatos (estado actual) |
| `sparse/hot-path/sort_topk_partial` | **0.94495 ms** | Fix candidato 2 (`select_nth_unstable_by` + sort top-10) |
| `sparse/hot-path/serialize_read_parse_one` | **1.3845 µs** | Parse `serde_json::from_str` de un sparse by hit (hot-path) |
| `sparse/hot-path/serialize_check_one` | **1.2158 µs** | Escritura `serde_json::to_string` (write path) |

Candidatos materializados por query: **5.000** (todos con sparse → parse por hit × 5.000).

## 3. Atribución de impacto

| Candidato | Coste en search_total | % del hot-path | Decisión |
|---|---|---|---|
| **2. sort completo** | 2.3748 ms | **0.51%** | Ahorro del fix topo parcial: 1.43 ms = **0.31%** → <1% |
| **1. parse serialize por hit** | 1.3845 µs × 5.000 = **6.92 ms** | **1.49%** | ≥1%, pero el fix No es un micro-opt (ver §4) |

## 4. Decisión del gate — WONF

### Candidato 2 — sort completo + truncate: ✅ WONFIX
**Impacto: 0.51% del hot-path; ahorro del fix 0.31%** — ambos < 1% (umbral del contrato).
El sort come el 5^ del costo del hot-path en este dataset representativo. Aunque
`select_nth` parcial es trivial en código plano, su banda de mejora real (1.43 ms/query)
está por debajo del umbral exigido. No se indica para implementación. Las metricas
reales confirman que el cuello de botella del hot-path sparse está en el recorrido
posting + decode + get_many (≈464 ms), no en el orden final.

### Candidato 1 — serialización JSON del sparse: ✅ WONFIX (con nota → P2-7)
- El parse por hit aporta **1.49%** (just (por encima del 1% nominal), pero el fix no es un
  diff mínimo:
  - El sparse vive como **`FieldValue::String(serde_json)`** en el **formato persistido**
    del node (`SPARSE_VECTOR_EXT_KEY`). Eliminarlo/zero-copy implica **cambiar el formato
    de persistencia** + migración + compat de lectura — un redesign de storage, no un
    micro-hot-path-opt. Ya está indexado como deuda **P2-7**
    (`src/sdk/serialization/mod.rs:227-294` — "serialización completa sin zero-copy").
  - Beneficio medido (`~6.9 ms/query` de un total de 464 ms) no justifica el riesgo de
    migración de datos en un gate de "diff mínimo".
  - La variante **write path** (`to_string`, P2-7) ni siquiera está en el hot-path de
    búsqueda; es e carga/escritura.

Ambos micro-candidatos del AUDIT-02 quedan **WONTFIX**. El sort completo es <1% (0.51%)
y la serialización, aunque alcanza ~1.5% del hot-path, exige un diff de persistencia
(migra) quedar P2-7. **Ningún cambio de código: producción se introduce**. La tarea se
cierra con el reporte de información a como evidencia, cumpliendo el contrato
("decisión válida en ambos sentidos").
