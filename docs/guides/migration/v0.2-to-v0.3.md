# Migration Guide: VantaDB v0.2 → v0.3

> **Note:** The v0.3 release was subsequently consolidated into v0.4.0 (the first public release). This guide covers the
> upgrade path for users running v0.2-era databases who need to migrate to the v0.3 storage format and API surface.
> Users on v0.2 should upgrade to v0.3 first, then to v0.4.0. See the [v0.3-to-v0.4](./v0.3-to-v0.4.md) guide for the
> next step.

## Summary

| Item | v0.2 | v0.3 |
|------|------|------|
| **Vector Index Format** | VNDX v1–v6 (deprecated) | VNDX v7 (unified) |
| **Schema Version** | `VTDBv001` v0 (legacy) | `VTDBv001` v1 |
| **WAL Format** | ad-hoc / inconsistent | `VWAL` v1 (standardised header) |
| **CLI** | `vanta-db` binary | `vanta` binary (unified) |
| **Python SDK** | `vantadb` (stub) | `vantadb_py` (PyO3 bindings) |
| **Serialization** | bincode (mixed versions) | postcard (vector index) |
| **Migration Engine** | none | `vanta migrate` subcommand |

### Upgrade Timeline

```
v0.2  ──────→  v0.3  ──────→  v0.4.0
 (legacy)     (storage fmt)   (first public release)
```

**Estimated migration time:** 5–15 minutes per database, depending on size and whether a full index rebuild is needed.

## Prerequisites

Before starting, ensure you have:

1. **VantaDB v0.3 binary** (or later): Download from the [releases page](https://github.com/your-org/vantadb/releases).
2. **Backup of your v0.2 database** (required — see [Backup](#1-backup) below).
3. **Filesystem space** for format migration: expect a temporary copy of the database during VantaFile migration
   (~2× the `vector_store.vanta` size).
4. **Python ≥3.10** if using the Python SDK.
5. **Node.js ≥18** if using the TypeScript SDK.

### Check Your Current Version

```shell
# v0.3+ binary
vanta --version

# v0.2 legacy binary
vanta-db --version
```

### Health Check Before Migration

Run a pre-migration health check to detect known issues:

```shell
# If on v0.3+
vanta migrate check /path/to/db
```

If the check reports `IncompatibleFormat` errors for the Vector Index, your database is still on an older format
and needs migration.

## Breaking Changes

### 1. Vector Index Format: VNDX v7 (exact match required)

**Impact:** Existing `index.bin` files from v0.2 use `VECTOR_INDEX_VERSION` ≤ 6. VantaDB v0.3 enforces an **exact
version match** on `VNDX` headers — a version mismatch produces an `IncompatibleFormat` error and the database will
not open.

**Affected file:** `index.bin` in each database directory.

**Error seen on open:**

```
IncompatibleFormat: Expected VNDX v7, found VNDX v3
```

**Migration action:** The index is a **derived format** — it is rebuilt from the canonical VantaFile data.
See [steps below](#2-migrate-the-vector-index).

### 2. Schema File Version Bump

**Impact:** The `.vanta.schema` file now uses `StorageHeader` with `version = 1` and `min_compat_version = 0`.
Older schema files that lack a proper header (pre-versioning) will be detected and rewritten.

**Affected file:** `.vanta.schema` in each database directory.

**Error seen on open:**

```
Schema version 0 is incompatible with this software (requires 1)
```

**Migration action:** The `vanta migrate` command handles this automatically
(see [below](#3-run-the-migration-engine)).

### 3. CLI Binary Rename: `vanta-db` → `vanta`

**Impact:** All commands that used `vanta-db` must use `vanta` instead. Scripts and CI pipelines referencing the old
binary name will fail.

| v0.2 (old) | v0.3 (new) |
|------------|------------|
| `vanta-db serve` | `vanta serve` |
| `vanta-db query` | `vanta query` |
| `vanta-db ingest` | `vanta ingest` |
| `vanta-db migrate` | `vanta migrate` |

**Migration action:** Update scripts to use `vanta` instead of `vanta-db`.

### 4. WAL Format Standardised

**Impact:** v0.2 WAL segments may have used inconsistent headers or no version marker at all. v0.3 enforces a
`VWAL` header with version field. Old WAL segments that fail validation are **skipped and rotated** — queued
mutations in pending segments may be lost if they were not checkpointed.

**Affected file:** `wal.log` and WAL segment files.

**Error seen on open:**

```
WALVersionMismatch: Expected VWAL v1, found WAL from v0.2 (no header)
```

**Migration action:** Follow the WAL drain procedure in [steps below](#1-drain-and-rotate-the-wal).

### 5. Python SDK Rename & API Changes

**Impact:** The Python package was renamed from `vantadb` (a thin stub in v0.2) to `vantadb_py` with full PyO3
bindings in v0.3. Import paths changed.

| v0.2 (old) | v0.3 (new) |
|------------|------------|
| `import vantadb` | `import vantadb_py as vantadb` |
| `VantaClient()` | `vantadb.Client()` |
| `client.query()` | `client.search()` |

### 6. Serialization Library Switch

**Impact:** The vector index (`index.bin`) now uses **postcard** instead of **bincode** for node payload
serialization. This is transparent to the user because the index is rebuilt during migration, but any external code
that reads index files directly must be updated.

## Migration Steps

### 1. Backup

```shell
# Full database directory backup
cp -r /path/to/db /path/to/db.v0.2-backup

# Verify backup
diff -r /path/to/db /path/to/db.v0.2-backup > /dev/null && echo "BACKUP OK"
```

> **⚠️ Required:** Do not skip this step. Migration is one-way for the index format. If the migration is interrupted,
> you must restore from backup.

### 2. Drain and Rotate the WAL

Ensure all pending WAL records are checkpointed to the backend storage before migrating:

```shell
# Forcibly checkpoint all pending WAL entries
vanta wal checkpoint /path/to/db --force

# Verify WAL is empty
vanta wal info /path/to/db
# Expected output: "WAL: 0 pending records"
```

After checkpointing, rotate to the new v0.3 WAL format:

```shell
# Rename old WAL (safe to remove after v0.3 migration completes)
mv /path/to/db/wal.log /path/to/db/wal.log.v0.2-legacy
```

VantaDB v0.3 will create a fresh `wal.log` with a `VWAL` v1 header on next open.

### 3. Run the Migration Engine

```shell
# Step 1: Preview what will be migrated
vanta migrate plan /path/to/db

# Expected output (example):
#   [Schema] v0 → v1: rewrite header
#   [Index]  v3 → v7: rebuild from VantaFile
#   [WAL]    none: already drained

# Step 2: Execute the migration (--dry-run first to verify)
vanta migrate run /path/to/db --dry-run

# Step 3: Run the actual migration
vanta migrate run /path/to/db

# Step 4: Run a post-migration integrity check
vanta migrate check /path/to/db
# Expected output: "No integrity issues found"
```

#### Additional Options

```shell
# Migrate a single format (e.g., only the schema)
vanta migrate run /path/to/db --format schema

# Skip confirmation prompts (automation)
vanta migrate run /path/to/db --force

# Verbose output (detailed timing per format)
vanta migrate run /path/to/db --verbose
```

### 4. Rebuild the Vector Index (if not done by migration)

If the migration engine reports that the index format is newer than the migration engine supports, or the index is
empty after migration, rebuild explicitly:

```shell
# Rebuild HNSW index from canonical VantaFile data
vanta index rebuild /path/to/db

# Verify index is healthy
vanta index stats /path/to/db
```

### 5. Verify the Migrated Database

```shell
# Open and run a basic query
vanta query /path/to/db "SELECT * FROM vectors LIMIT 5"

# Check version info
vanta info /path/to/db

# Expected output:
#   Schema version: 1
#   Index version:  7
#   WAL format:     VWAL v1
```

### 6. Update Client Libraries

#### Python SDK

```shell
pip uninstall vantadb        # remove v0.2 stub
pip install vantadb-py        # install v0.3+ bindings
```

```python
# v0.3+ API
import vantadb_py as vantadb

client = vantadb.Client("/path/to/db")
results = client.search("query vector", top_k=10)
```

#### TypeScript SDK

```shell
npm uninstall vantadb
npm install vantadb-ts
```

```typescript
// v0.3+ API
import { VantaClient } from 'vantadb-ts';

const client = new VantaClient('/path/to/db');
const results = await client.search('query vector', { topK: 10 });
```

## Rollback

### If Migration Fails Mid-Way

The migration engine uses **backup markers** — it renames the original file before writing the new version. If the
process is interrupted, the marker is detected on the next run:

```shell
# Migration engine auto-detects leftover backup markers:
vanta migrate run /path/to/db
# Output: "Found backup marker from previous migration attempt. Restore? [y/N]"
```

**Manual restore from backup marker:**

```shell
# List backup markers
ls /path/to/db/*.backup

# Restore a specific format
mv /path/to/db/index.bin.backup /path/to/db/index.bin
mv /path/to/db/vector_store.vanta.backup /path/to/db/vector_store.vanta
```

### Full Rollback to v0.2

```shell
# 1. Stop the v0.3 processes
# 2. Restore the full backup
rm -rf /path/to/db
cp -r /path/to/db.v0.2-backup /path/to/db

# 3. Reinstall v0.2 binary
# 4. Reinstall v0.2 client libraries
pip install vantadb==0.2
```

> **⚠️ Rollback limitation:** WAL records written with the v0.3 `VWAL` format cannot be read by the v0.2 WAL reader.
> After rolling back, any mutations that were committed by v0.3 but not yet checkpointed to VantaFile are lost
> unless you replay them manually.

### Rollback Constraints

| Format | Rollback Possible? | Notes |
|--------|-------------------|-------|
| Schema (.vanta.schema) | ✅ Yes | Schema v1 can be rewritten to v0; no data loss |
| Vector Index (index.bin) | ❌ No* | Rebuild from VantaFile data with `vanta index rebuild --version 3` if v0.2 binary supports it |
| VantaFile | ✅ Yes | No format change in v0.2 → v0.3 (stays v1) |
| WAL | ⚠️ Partial | Old segments (v0.2) are readable; new segments (v0.3) are not |

## Verification

### Automated Verification

```shell
# Full integrity check
vanta migrate check /path/to/db

# Query test — confirm vector search works
vanta query /path/to/db "SELECT id, vector FROM vectors LIMIT 1"
```

### Manual Verification Checklist

- [ ] `vanta migrate check /path/to/db` reports **no issues**
- [ ] `vanta info /path/to/db` shows `Schema version: 1` and `Index version: 7`
- [ ] Vector search returns expected results (compare known queries against pre-migration output)
- [ ] WAL is active: insert a vector, checkpoint, confirm persistence
- [ ] Python SDK connects: `import vantadb_py; vantadb.Client("/path/to/db")`
- [ ] TypeScript SDK connects: `new VantaClient("/path/to/db")`
- [ ] All scripts updated from `vanta-db` to `vanta` binary name
- [ ] Backup file (`db.v0.2-backup/`) can be deleted after confirmation

### Rollback Decision Tree

```
Migration succeeded?
├── Yes → Delete backup: rm -rf /path/to/db.v0.2-backup
└── No  → Bugs or data loss?
         ├── Minor issues → Fix in-place, re-run migrate check
         └── Critical issues → Restore from backup (see Rollback section)
```

## Troubleshooting

### "IncompatibleFormat: Expected VNDX v7, found VNDX v3"

The migration engine did not rebuild the index. Run:

```shell
vanta migrate run /path/to/db --format index
```

### "WALVersionMismatch" on Open

Old WAL segments were not drained before upgrade. Follow the [drain procedure](#2-drain-and-rotate-the-wal) above,
then reopen the database.

### "Schema version 0 is incompatible"

The migration skipped schema migration. Run:

```shell
vanta migrate run /path/to/db --format schema
```

### Migration Engine Reports "No migrations needed" But Old Format Exists

The v0.3 binary you are running may not have the migration engine for VNDX v7 (e.g., you are on an intermediate
v0.3-alpha). Upgrade to the latest v0.3 stable release.

### Backup Marker Detected on Fresh Migration

A previous migration attempt was interrupted. Confirm restore when prompted, or manually clean up:

```shell
ls /path/to/db/*.backup  # inspect markers
rm /path/to/db/*.backup   # remove if you have a full backup
```
